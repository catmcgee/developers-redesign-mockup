Docs Research

Why this mockup is structured the way it is: the brief it implements, the research into docs navigation, and every source.

Copy MarkdownOpen ▾

Question: should use cases be the top-level navigation of solana.com/docs?
Answer: use cases should be the entry point (Start here, the job picker, the paths), not several top-level tabs. Keep one canonical core organised by subject, and put the use-case domains in one tab.

1. The brief

This mockup implements an internal Notion brief, “TL;DR: solana.com/developers becomes a job picker” [1], shared at the start of this work (12 Oct 2026). Its core claims:

  • Thesis. “Every developer enters through a problem they already have, and leaves with something working. Solana fundamentals are never an initial blocker.”
  • Evidence. MLH focus group (Sept 2026): participants couldn't say what Solana is or what they'd build; they compared it with Stripe and databases, not other chains; concepts arrived without context; examples ended with no next step. MLH recommended explaining Solana through questions web2 developers already ask.
  • Five principles. Name the outcome · fundamentals just in time (two sentences, a web2 analogy, a docs link) · no concept gate before first success · use it, then show it live · end in their stack.
  • Wave 1 paths. Accept dollar payments · Charge a few cents per API call · Issue a tokenized asset with compliance controls. Wave 2: shared audit record, game items.
  • Six-stage path template, phasing (Align → Pilot (Payments) → Build → Validate), owners (Awesome Docs team, Playground team, Bri for video), and three open decisions (Wave 1 paths; where “web3” appears; how to run the assessment).

2. Method

Three research tracks ran in parallel on 13 Oct 2026, plus inspection of the live site and repo while building the mockup:

  1. Platform survey. Live top-level navigation of 21 developer docs sites, parsed from page HTML where possible.
  2. Literature and frameworks. Empirical studies of how developers use API docs, survey and traffic data, IA frameworks, AI-agent consumption.
  3. Solana's own docs. The public solana-foundation/solana-com repo: IA, git and PR history, overlap counts; plus documented redesigns elsewhere.

Not checked: internal analytics, Linear, or internal research behind unauthorised connectors.

4. What the research says

  • Start from the scenario. “Matching APIs with scenarios” was a key need among 440+ Microsoft developers; scenario docs “can compensate for hard-to-understand API structure” [30]. Developers spend ~49% of task time in docs and are both opportunistic and systematic [31][33].
  • Organise by what the developer is doing, not by content type. A top level split into Concepts / Samples / Reference confused participants [31]; a use-case-oriented redesign gave fewer errors and faster tasks (n=22, changes bundled) [32].
  • But task and audience schemes are ambiguous. Mixing schemes in one menu “almost guarantees confusion” [37]; audience-based navigation degraded usability in testing because users fit several buckets [38][39].
  • Fragmentation and duplicated scenarios are top complaints [34]; findability and organisation matter to most practitioners [35].
  • Diátaxis allows another axis at the top with the four types beneath, and warns against empty top-down structures [36]. Top Tasks: a few tasks carry most demand, so keep the entry list short and data-driven [40].
  • Every page is page one. Readers arrive by search, so pages must stand alone and link richly [41].

Strength of evidence: studies are small and mostly pre-AI; nothing tests use-case versus product navigation head-to-head for a blockchain platform.

5. What AI agents change

  • Agents are roughly half or more of docs traffic on vendor platforms (Mintlify ~45% in 2025, reported 66% by Aug 2026; GitBook ~52%) [50][51][52].
  • They navigate by links, llms.txt and .md pages, not tabs: 86–97% of fetches via links [53]; llms.txt cut 404s about 20× [51]. Counterpoint: 97% of llms.txt files site-wide get no requests [54].
  • Humans still verify: technical docs are the top learning resource (67.8%) and 46% distrust AI output [55].
  • Implication: the menu matters less, single sources and links matter more. Duplicated explanations hand agents conflicting answers.

6. What Solana's docs look like today

  • Six tabs today: Start here · Concepts · RPC API · Finance · Video Tutorials · Resources [60]. The use cases are already one tab, Finance, added in #1767 (29 Jul 2026) as part 2 of the docs restructure stack [61]. Payments was added in #1061 (16 Jan 2026) [62]. None of these PRs cite user research or analytics.
  • Thin sections: payments 30 pages, defi 9 (5 are one DvP program), tokenization 5, finance 2. For comparison: rpc 91, tools 197.
  • Leaky borders: DvP in two roots; x402 in three places; Solana Pay in two; #2127 moved Production Readiness and the x402 facilitator out of Payments [63].
  • Re-explained basics: 19 of 30 payments pages discuss token accounts, only 5 link to /docs/tokens; how-payments-work re-explains accounts, ATAs, token programs, fees and transactions.
  • Already instrumented: per-section llms.txt, .md versions of every page, and PostHog logging of Markdown requests by route.

7. Redesigns elsewhere

  • GitLab moved its docs nav to workflow-based groups after usability testing (“improved overall success rates”), and its guidelines warn against a long top-level nav [70][71]. Its UI nav moved to task groups after card sorts and a longitudinal study [72].
  • Twilio reorganised its Console by lifecycle after card sorts and removed ~10% duplicate content [73].
  • GOV.UK dropped audience-based navigation after testing [39]. Gatsby and Kubernetes organise by content type [74].
  • No documented case was found of a company moving away from use-case tabs, and none published measured outcomes for either direction.

9. Validate before shipping

  1. Top-tasks survey (MLH participants + current docs users) to confirm the 3–7 jobs in the picker [40].
  2. Tree test of today's nav versus this one, with web2 and crypto-native groups [70][73].
  3. PostHog Markdown-request data and search logs by section, to see what agents and people actually pull.
  4. MLH rerun question from the brief: after the first screen, can participants say what Solana is and what they'd build?
