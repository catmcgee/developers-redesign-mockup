Docs Research

Why this mockup is structured the way it is: the brief it implements, the research into docs navigation, and every source.

Copy MarkdownOpen ▾

Question: should use cases be the top-level navigation of solana.com/docs?
Answer: not as fine-grained jobs (“Charge per API call”) in the global nav; no leading docs site does that. Yes as a few domain tabs, the Stripe / Circle / Coinbase pattern: Payments · Assets · Markets, the three pieces of internet capital markets. Each opens with its job path, then guides. Underneath sits one shared core: How Solana works · Developer resources (including Programs) · API reference.

1. The brief

This mockup implements an internal Notion brief, “TL;DR: solana.com/developers becomes a job picker” [1], shared at the start of this work (12 Oct 2026). Its core claims:

  • Thesis. “Every developer enters through a problem they already have, and leaves with something working. Solana fundamentals are never an initial blocker.”
  • Evidence. MLH focus group (Sept 2026): participants couldn't say what Solana is or what they'd build; they compared it with Stripe and databases, not other chains; concepts arrived without context; examples ended with no next step. MLH recommended explaining Solana through questions web2 developers already ask.
  • Five principles. Name the outcome · fundamentals just in time (two sentences, a web2 analogy, a docs link) · no concept gate before first success · use it, then show it live · end in their stack.
  • Wave 1 paths. Accept dollar payments · Charge a few cents per API call · Issue a tokenized asset with compliance controls. Wave 2: shared audit record, game items.
  • Six-stage path template, phasing (Align → Pilot (Payments) → Build → Validate), owners (Awesome Docs team, Playground team, Bri for video), and three open decisions (Wave 1 paths; where “web3” appears; how to run the assessment).

2. Method

Three research tracks ran in parallel on 13 Oct 2026, plus inspection of the live site and repo while building the mockup:

  1. Platform survey. Live top-level navigation of 21 developer docs sites, parsed from page HTML where possible.
  2. Literature and frameworks. Empirical studies of how developers use API docs, survey and traffic data, IA frameworks, AI-agent consumption.
  3. Solana's own docs. The public solana-foundation/solana-com repo: IA, git and PR history, overlap counts; plus documented redesigns elsewhere.

Not checked: internal analytics, Linear, or internal research behind unauthorised connectors.

4. What the research says

  • Start from the scenario. “Matching APIs with scenarios” was a key need among 440+ Microsoft developers; scenario docs “can compensate for hard-to-understand API structure” [30]. Developers spend ~49% of task time in docs and are both opportunistic and systematic [31][33].
  • Organise by what the developer is doing, not by content type. A top level split into Concepts / Samples / Reference confused participants [31]; a use-case-oriented redesign gave fewer errors and faster tasks (n=22, changes bundled) [32].
  • But task and audience schemes are ambiguous. Mixing schemes in one menu “almost guarantees confusion” [37]; audience-based navigation degraded usability in testing because users fit several buckets [38][39].
  • Fragmentation and duplicated scenarios are top complaints [34]; findability and organisation matter to most practitioners [35].
  • Diátaxis allows another axis at the top with the four types beneath, and warns against empty top-down structures [36]. Top Tasks: a few tasks carry most demand, so keep the entry list short and data-driven [40].
  • Every page is page one. Readers arrive by search, so pages must stand alone and link richly [41].

Strength of evidence: studies are small and mostly pre-AI; nothing tests use-case versus product navigation head-to-head for a blockchain platform.

5. What AI agents change

  • Agents are roughly half or more of docs traffic on vendor platforms (Mintlify ~45% in 2025, reported 66% by Aug 2026; GitBook ~52%) [50][51][52].
  • They navigate by links, llms.txt and .md pages, not tabs: 86–97% of fetches via links [53]; llms.txt cut 404s about 20× [51]. Counterpoint: 97% of llms.txt files site-wide get no requests [54].
  • Humans still verify: technical docs are the top learning resource (67.8%) and 46% distrust AI output [55].
  • Implication: the menu matters less, single sources and links matter more. Duplicated explanations hand agents conflicting answers.

6. What Solana's docs look like today

  • Six tabs today: Start here · Concepts · RPC API · Finance · Video Tutorials · Resources [60]. The use cases are already one tab, Finance, added in #1767 (29 Jul 2026) as part 2 of the docs restructure stack [61]. Payments was added in #1061 (16 Jan 2026) [62]. None of these PRs cite user research or analytics.
  • Thin sections: payments 30 pages, defi 9 (5 are one DvP program), tokenization 5, finance 2. For comparison: rpc 91, tools 197.
  • Leaky borders: DvP in two roots; x402 in three places; Solana Pay in two; #2127 moved Production Readiness and the x402 facilitator out of Payments [63].
  • Re-explained basics: 19 of 30 payments pages discuss token accounts, only 5 link to /docs/tokens; how-payments-work re-explains accounts, ATAs, token programs, fees and transactions.
  • Already instrumented: per-section llms.txt, .md versions of every page, and PostHog logging of Markdown requests by route.

7. Redesigns elsewhere

  • GitLab moved its docs nav to workflow-based groups after usability testing (“improved overall success rates”), and its guidelines warn against a long top-level nav [70][71]. Its UI nav moved to task groups after card sorts and a longitudinal study [72].
  • Twilio reorganised its Console by lifecycle after card sorts and removed ~10% duplicate content [73].
  • GOV.UK dropped audience-based navigation after testing [39]. Gatsby and Kubernetes organise by content type [74].
  • No documented case was found of a company moving away from use-case tabs, and none published measured outcomes for either direction.

Revision history

Third revision. Programs moved from its own tab into Developer resources, following Stripe, and is linked from Start here. That brings the bar to seven tabs.

Second revision. A “Develop” tab (programs plus tools) was briefly modelled on Base and Sui. It was replaced after review by benchmarks from the strongest web2 and institutional-finance docs: Stripe (Developer resources), Shopify (Functions nested in Apps) and Canton (App Development as a top-level tab). Programs keeps its own tab, and tools move to Developer resources.

First revision. An earlier version of this mockup collapsed everything into a single “Use cases” tab, mainly because some of Solana's use-case sections are thin today (tokenization 5 pages, defi 9). On review that overweighted a snapshot of current page counts. It also departed from the closest precedents, Stripe above all, which put their domains at the top level. A single generic “Use cases” label also says nothing about what's inside. The thin-section risk is handled instead by folding tokens into Assets, and by a fold-back rule for Markets if it doesn't grow (see the design notes on that tab).

9. Validate before shipping

  1. Top-tasks survey (MLH participants + current docs users) to confirm the 3–7 jobs in the picker [40].
  2. Tree test of today's nav versus this one, with web2 and crypto-native groups [70][73].
  3. PostHog Markdown-request data and search logs by section, to see what agents and people actually pull.
  4. MLH rerun question from the brief: after the first screen, can participants say what Solana is and what they'd build?

Appendix A: the brief, in full

Reproduced from the Notion brief [1] as shared on 12 Oct 2026. Formatting adapted for this page.

TL;DR

solana.com/developers becomes a job picker: every developer enters through a problem they already have, and leaves with something working. Solana fundamentals are never an initial blocker.

Each concept appears only at the step of a build that needs it, preferably explained against something the developer already knows.

We ship three use cases / job paths first (stablecoin payments, pay-per-call APIs, Tokenized Assets), on one shared path template, and validate by rerunning the MLH focus group / Creating our own.

Why

Web2 / “regular” developers arrive with a problem to solve; today's page answers "why Solana over other chains" and teaches concepts before showing anything they can build.

  • MLH focus group (Sept 2026): participants could not say what Solana is or what they would build with it. They compared it to Stripe and traditional databases, not other chains. Concepts like transactions, accounts and framework choice arrived without context, and examples ended with no next step. MLH's recommendation: explain Solana through the questions web2 developers already ask.
  • Developers land on concept-heavy pages (keypairs, decentralization) and disengage. We should lead with concrete use cases and weave fundamentals in.
  • Existing flags: the solana.com Build dropdown already has a "Build by use case" column (Payments, DeFi, Gaming, Token Extensions, Agents and AI), but it sits third.

Principles

Every job path is held to these rules:

  1. Name the outcome. "Charge per API call", not "SPL tokens". The developer should recognise their own problem in the title.
  2. Fundamentals arrive just in time. A concept appears only at the step that uses it. It gets at most two sentences, a web2 analogy, and a link to docs for depth.
  3. No concept gate before first success. Nothing to read, install or decide before the developer sees their result working. The first success happens in the browser playground; local "try it yourself" guides, installation and setup come after it.
  4. Use it, then show it live. Before building, the developer uses the product as a customer would (a wallet, a stablecoin received) then sees the real network doing that job right now, not a mock (This builds on principle 3)
  5. End in their stack. The last build step runs from the developer's own machine, then offers the next path or a guided program.

Page architecture

The landing page has one job: get the developer into the right path within one scroll. Top to bottom:

  1. What Solana does for them, with no chain vocabulary. Draft: "A shared global ledger your code runs on. Payments and records settle in under a second for a fraction of a cent."
  2. One module showing the network working now: throughput, median fee, finality.
  3. "What are you building?" job picker. One card per job path: the developer's question as the title, one line on fit, one button into the path.
  4. Guided routes such as Docs, Solana School, Ecosystem partners for developers who want a structured start.

Mockup of the job picker (item 3), structure only, not final copy or design: job-picker-mockup.html

There is no standalone concepts section on the landing page.

Navigation changes compared to solana.com: the existing "Build by use case" column moves first in the Build dropdown and becomes the job-path list, each entry relabelled as the developer's question ("Payments" → "Accept dollar payments").

Concepts / Technology (Token Extensions as an example) leaves that dropdown and folds into the use case / job path (Tokenised assets as an example), since they are primitives, not a job.

Start building and Tools and references follow behind it.

The job paths

The following is an idea for the initial job paths, mentioning what the user would build and which fundamentals they would learn.

Path (the developer's question)What they buildFundamentals picked up
Wave 1 · Accept dollar payments that settle in secondsA checkout that takes a stablecoin payment and confirms it server-sideWallets and signatures, transactions, token accounts, confirmation
Wave 1 · Charge a few cents per API callA paywalled API endpoint that unlocks after paymentTransaction fees, RPC, verifying a payment from a backend
Wave 1 · Issue a tokenized asset with compliance controlsA token with metadata, transfer rules and a freeze/pause controlAccounts, mint authority, programs (Token-2022), extensions
Wave 2 · Keep a shared record partners can auditA small program that records who changed what, queried from an appWriting a program, accounts as state, PDAs, Anchor
Wave 2 · Let players own items across gamesAn item minted to a player and read by a second appTokens as ownership, metadata, reading state

Anatomy of a job path

Every path follows the same six stages, so the team builds one template and fills it per job.

StageWhat the developer doesFundamentals picked up here
1. The jobA problem they already have, in their wordsNothing yet: plain language, no chain vocabulary
2. Fit checkWhere Solana fits, and where it does notFees and settlement time
3. Use it, then see it liveReceive a stablecoin in a wallet, then watch itTransactions and the explorer: a transaction is a signed request, here is one
4. Build it in the browserFirst success in the playground, no installWallets, accounts, programs: only those this build touches, two lines each
5. Plug it into your stackSame result from their own backend and SDKRPC, confirmation, fees in production
6. Go furtherNext job path, deep docs, or a guided programDepth on demand: links into docs

Fundamentals coverage map

Across the five paths, every core concept is taught at least once, always inside a build.
