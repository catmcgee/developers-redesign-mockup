1 · The job

Accept dollar payments that settle in seconds

You sell something online and want to get paid in dollars by anyone, anywhere. You want the money in your account in seconds rather than days, with no 3% cut and no chargebacks.

You'll finish with: a checkout button that takes a 1 USDC payment and a server endpoint that confirms it was paid before you ship the order.

▶ 2-minute walkthrough (optional)Video · Bri
Plain language only, no chain vocabulary. "USDC" is the only new word, and it's glossed as "digital dollars" on the card. The video is optional and sits beside the content, so it doesn't gate anything.
2 · Fit check

Is this the right tool for your payments?

Cards (e.g. Stripe)Bank transferStablecoin on Solana
Fee on a $20 sale~$0.88 (2.9% + 30¢)$0–$30~$0.001
Money usable by you2 business days1–5 days< 1 second
ChargebacksYesRareNo. Refunds are a payment you send back.
Customer needsA cardA bank accountA wallet holding USDC

A good fit if

  • You sell across borders or to people without cards
  • Your margins or ticket sizes are small
  • You want instant payouts or programmable splits

Not the right fit if

  • Your customers won't hold a wallet and you won't onboard them (keep cards, or add an on-ramp)
  • You need card-style buyer protection
  • You haven't checked how your jurisdiction treats stablecoins
◆ Fees How fees work →
Every transaction pays a small flat network fee, currently about a tenth of a cent, no matter the amount. Whoever submits the transaction pays it, and you can choose to cover it for your customers.
Like: a fixed per-API-call cost, not a percentage interchange fee.
The "Not the right fit" column is the most important box on the page for credibility. MLH participants compared Solana with Stripe, so we answer that comparison honestly and in its own terms.

4 · Build it in the browser

Build the checkout. Nothing to install.

Here's the code for the button you just used. Change the store name and price, then pay with your test wallet.

Playground · checkout.tsx[ Run ▶ ]
import { PaymentButton } from "@solana-commerce/kit";

export default function Checkout() {
  return (
    <PaymentButton
      config={{
        merchant: {
          name: "My Sticker Shop",
          wallet: "8f3k…Qz1w", // ◆ address
        },
        mode: "fixed", amount: "1.00",
        currency: "USDC",
      }}
      onPaymentSuccess={(sig) =>
        console.log("paid", sig)} // ◆ signature
    />
  );
}

◆ Address Accounts →
The store's wallet address is where payments land. Anyone can send to it, and only the key holder can move money out.
Like: an IBAN that also works as a username.
This is the first-success moment, and it's built on the Commerce Kit playground that already exists (launch.solana.com/products/commercekit/playground). It takes about five minutes from landing. Only the concepts this code actually touches appear here: the address, and the signature that comes back.
Today's Payments quickstart opens with pnpm add and "You need Node.js 20+, a React or Next.js app", and the browser playground sits below that. The pilot's biggest content change is simply flipping that order.
5 · Plug it into your stack

Confirm payments from your own backend

A button in the browser can be faked, so your server should only ship the order after it checks the payment on the network itself. You'll run this on your machine against devnet, then switch one URL for production.

Next.js routeNode / ExpressPythoncurl
// app/api/orders/[id]/confirm/route.ts
const rpc = createSolanaRpc(process.env.RPC_URL);           // ◆ RPC
const tx  = await rpc.getTransaction(signature, {
  commitment: "confirmed",                                  // ◆ confirmation
}).send();

if (!tx || tx.meta.err) return fail("not paid");
assertPaid(tx, { to: STORE_USDC_ACCOUNT, mint: USDC_MINT, amount: order.total, reference: order.id });
await markOrderPaid(order.id);  // idempotent: the same signature can't pay twice
◆ RPC RPC & providers →
RPC is the HTTP API your code uses to read from and send to the network. Use a free public endpoint for testing, and a provider in production.
Like: a hosted database endpoint, with providers in the role of AWS or Supabase.
◆ Confirmation levels Commitment →
A transaction moves from processed to confirmed to finalized. For most orders confirmed is enough. Wait for finalized when the amounts are large.
Like: pending → authorized → settled.
◆ Fees in production Fee sponsorship (Kora) →
By default your customer pays the network fee in SOL, which means they need some SOL. To remove that step, sponsor the fee yourself.
Like: absorbing the card fee instead of adding a surcharge.

Before you go live

  • Swap the devnet RPC URL and USDC mint for mainnet ones
  • Match payments to orders with a reference key, not by amount
  • Handle expired or failed transactions, since customers retry
  • Receive webhooks instead of polling (indexing guide)
  • Decide who pays network fees
This stage carries the path's real engineering lesson: the server verifies on its own and never trusts the client. RPC, confirmation and fee concepts show up here because this is the first time they matter. Before production they'd just be noise.
Installation and setup (the CLI, a local validator) aren't required here. All this needs is npm i @solana/kit and a URL. The "Install the Solana CLI" docs are linked as optional.

Wave 1 covers everything a developer needs to use Solana. Writing a program, PDAs and CPI only arrive in Wave 2. That's the real trade-off behind the open decision "swap one path for a program-writing path". My recommendation is to keep the Wave 1 paths as proposed. Web2 developers build on existing programs (Token-2022, payments) long before they write one, and the current Quick Start already covers programs, PDAs and CPI. It just moves to "Write programs" (see Docs IA).
CPI is uncovered across all five paths. Either the Shared record path calls the Token program (for example, issuing a receipt token) or CPI stays docs-only. Decide this when Wave 2 is scoped.
Rent is easy to miss and surprises people in production ("why does my first transfer to a new customer cost ~0.002 SOL extra?"). Payments should touch it in stage 5. It's fully introduced in the tokenized-asset path, where creating accounts is the whole job.
